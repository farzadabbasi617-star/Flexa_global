# راه‌اندازی VPS — چک‌لیست قبل از دادن دسترسی

این سند برای وقتی است که سرور مجازی خریدی و می‌خواهی نصب و راه‌اندازی را با کمک ایجنت انجام دهی.

---

## ۱) قبل از هر چیز: یک کاربر جدا بساز، root نده

با کاربر root به سرور وصل شو و این‌ها را اجرا کن. **این کارها را خودت انجام بده، نه ایجنت.**

```bash
# یک کاربر بدون دسترسی root
adduser --disabled-password --gecos "" deploy
usermod -aG sudo deploy

# پوشه کلید
mkdir -p /home/deploy/.ssh
chmod 700 /home/deploy/.ssh
touch /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh
```

## ۲) کلید عمومی ایجنت را اضافه کن

در ابتدای هر جلسه، ایجنت یک **کلید تازه** می‌سازد و کلید عمومی‌اش را به تو می‌دهد.
آن یک خط را در این فایل بگذار:

```bash
echo "ssh-ed25519 AAAA...  gament-agent" >> /home/deploy/.ssh/authorized_keys
```

> **چرا هر جلسه یک کلید تازه؟** حافظه ایجنت بین جلسات پاک می‌شود و کلید خصوصی از بین می‌رود.
> این در واقع یک مزیت امنیتی است: هیچ کلید ماندگاری وجود ندارد که لو برود.

## ۳) بعد از پایان کار، کلید را حذف کن

**این مهم‌ترین قدم است. فراموشش نکن.**

```bash
# کل دسترسی ایجنت را قطع می‌کند
> /home/deploy/.ssh/authorized_keys
```

یا فقط خط مربوط به ایجنت را پاک کن.

## ۴) امنیت پایه سرور (اول از همه اجرا کن)

```bash
# ورود root با پسورد را ببند
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh

# فایروال
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable

# آپدیت‌های امنیتی خودکار
apt update && apt install -y unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades
```

## آنچه ایجنت نصب خواهد کرد

| مورد | توضیح |
|---|---|
| Node.js 20 | نسخه‌ای که `package.json` مشخص کرده |
| nginx | reverse proxy روی پورت ۸۰/۴۴۳ |
| certbot | گواهی SSL رایگان + تمدید خودکار |
| systemd service | اجرای دائمی اپ، ریستارت خودکار بعد از کرش یا ریبوت |
| deploy hook | با هر push روی `main` خودکار دیپلوی شود |
| اسکریپت بکاپ | بکاپ روزانه دیتابیس |

**۴۰ متغیر محیطی** باید از Render منتقل شوند. ایجنت می‌تواند از API رندر بخواندشان.

---

## آنچه ایجنت **نمی‌تواند** انجام دهد

صادقانه بدان تا انتظار اشتباه نداشته باشی:

- **۲۴/۷ نیست.** اگر سرور ساعت ۳ صبح کرش کند، خبردار نمی‌شود. فقط وقتی حاضر است که تو با او صحبت کنی.
- **حافظه‌اش پاک می‌شود.** هر جلسه باید دوباره کلید بسازد و وصل شود.
- **مانیتورینگ ندارد.** برای هشدار قطعی سایت باید یک سرویس بیرونی (مثل UptimeRobot که رایگان است) وصل کنی.

پس **نگهداری واقعی همچنان با توست**؛ ایجنت موقع کار کردن کنارت هست، نه به‌جای تو.

## اطلاعاتی که موقع شروع باید بدهی

۱. **IP سرور**
۲. **نام کاربری** (اگر `deploy` نیست)
۳. **پورت SSH** (اگر ۲۲ نیست)
۴. تأیید اینکه دامنه `gament1.ir` را به IP جدید اشاره داده‌ای (رکورد A)

⚠️ **هرگز پسورد root را در چت نفرست.** فقط کلید عمومی ایجنت را روی سرور بگذار.

## نکات مهمی که موقع مهاجرت فراموش می‌شوند

### ۱. Webhook تلگرام
بات هنوز به Render وصل است. بعد از راه‌اندازی سرور جدید حتماً webhook را عوض کن،
وگرنه بات روی سرور قدیمی کار می‌کند و روی جدید هیچ پیامی نمی‌رسد.

### ۲. متغیرهای `NEXT_PUBLIC_*` در زمان build جاسازی می‌شوند
تغییر دادن‌شان در `.env.production` و ریستارت کردن **کافی نیست** — باید دوباره build کنی.

### ۳. رکورد DNS
قبل از گرفتن گواهی SSL، رکورد A دامنه باید به IP سرور جدید اشاره کند،
وگرنه certbot شکست می‌خورد.

### ۴. Cronهای گیت‌هاب
`telegram-cron.yml` و `gaming-news-cron.yml` آدرس سایت را صدا می‌زنند.
اگر دامنه عوض شود باید در secretهای مخزن هم به‌روز شود.

### ۵. Render را فوراً حذف نکن
تا وقتی مطمئن نشدی سرور جدید پایدار است، سرویس Render را نگه دار.
برگشتن به عقب فقط یک تغییر DNS است.

## پس از راه‌اندازی، دیپلوی چطور انجام می‌شود

```bash
cd /var/www/gament
sudo -u deploy git pull
sudo -u deploy npm ci
sudo -u deploy npm run build
sudo systemctl restart gament
```

اگر خواستی این خودکار شود، بگو تا یک workflow گیت‌هاب بنویسم که با هر push
روی `main` این کار را انجام دهد.

## بیلد سبک‌تر روی VPS: `output: standalone`

`next.config.ts` حالا این حالت را پشتیبانی می‌کند، ولی **فقط وقتی فعال می‌شود که خودت بخواهی**:

```bash
NEXT_OUTPUT_STANDALONE=true npm run build
```

**چرا پیش‌فرض خاموش است؟** رندر اپ را با `next start` بالا می‌آورد که مستقیم از `.next/`
می‌خواند. عوض‌کردن سراسری `output` یعنی تغییر در نحوهٔ بوت‌شدن سرویسِ زنده — و این
دیپلوی جای امتحان‌کردنش نیست. روی VPS آزادانه روشنش کن.

**چه چیزی عوض می‌شود:**

| | `next start` (فعلی) | `standalone` |
|---|---|---|
| حجم روی سرور | کل `node_modules` (~۱GB) | فقط وابستگی‌های واقعی (~۱۵۰MB) |
| اجرا | `npm run start` | `node .next/standalone/server.js` |
| نیاز به `npm ci` روی سرور | دارد | ندارد |

**نکتهٔ مهم:** بیلد standalone فایل‌های `public/` و `.next/static` را داخل پوشه کپی
**نمی‌کند**. باید دستی منتقل شوند وگرنه سایت بدون CSS و تصویر بالا می‌آید:

```bash
cp -r public .next/standalone/public
cp -r .next/static .next/standalone/.next/static
```

اگر این مسیر را انتخاب کردی، خط `ExecStart` در `/etc/systemd/system/gament.service`
باید به `/usr/bin/node /var/www/gament/.next/standalone/server.js` تغییر کند.

> ⚠️ **هنوز روی سرور واقعی تست نشده.** تأیید شده که پیش‌فرض خاموش است و بیلد عادی
> سالم کار می‌کند (پوشهٔ `standalone/` ساخته نمی‌شود). ولی خود بیلد standalone در
> سندباکس با کمبود حافظه (۲GB) شکست خورد و کامل اجرا نشد. **اولین بار روی VPS
> امتحانش کن، نه وسط یک دیپلوی فوری** — و تا وقتی سرویس بالا نیامده Render را نگه دار.

## تصمیم دیتابیس (بررسی‌شده ۳۱ جولای ۲۰۲۶)

**سؤال:** آیا می‌شود همزمان از Neon و دیتابیس روی VPS استفاده کرد؟

**پاسخ کوتاه: از نظر فنی بله، ولی نباید.** سه معنی متفاوت دارد:

### ۱. تقسیم داده بین دو دیتابیس ❌ خطرناک
مثلاً کاربرها روی Neon و روم‌ها روی VPS.

یک تراکنش نمی‌تواند دو دیتابیس را همزمان پوشش دهد. الان وقتی کاربری وارد روم می‌شود،
کسر پول از کیف پول، ثبت تراکنش و ثبت عضویت **در یک تراکنش اتمیک** انجام می‌شوند
(`joinCodRoom` در `src/lib/cod-room-service.ts`).

اگر این‌ها روی دو دیتابیس باشند، ممکن است **پول کسر شود ولی عضویت ثبت نشود** — با پول
واقعی کاربر. ضمناً ۱۳۵ فایل که از `@/db` استفاده می‌کنند باید بازنویسی شوند.

### ۲. یکی اصلی، یکی replica زنده ⚠️ زودهنگام
بررسی شد: **Neon اجازه replication می‌دهد** (`wal_level = replica`، کاربر مجوز دارد،
۱۰ slot آزاد است). یعنی از نظر فنی شدنی است.

ولی برای **۱۶ مگابایت داده و ۱۸ کاربر** پیچیدگی‌اش توجیه ندارد. این راه‌حلِ مشکلی است
که هنوز وجود ندارد. وقتی به چند هزار کاربر رسیدی دوباره بررسی شود.

### ۳. VPS اصلی + بکاپ در جای دوم ✅ **این را انجام بده**

```
دیتابیس زنده  ->  PostgreSQL روی خود VPS   (~۱ms به‌جای ~۴۰۰ms فعلی)
بکاپ روزانه   ->  فایل روی VPS (اسکریپت آماده است)
کپی دوم       ->  جایی خارج از VPS
```

**چرا:** تنها ریسک واقعیِ بردن دیتابیس روی VPS این است که اگر سرور بترکد یا سرویس‌دهنده
قطعش کند، اپ و دیتابیس **با هم** از بین می‌روند. بکاپ در جای دوم دقیقاً همین را پوشش
می‌دهد، بدون پیچیدگی دو دیتابیس فعال.

## کارهایی که هنگام خرید VPS باید انجام شود

این‌ها هنوز **انجام نشده‌اند** و منتظر خرید سرور هستند:

- [ ] `scripts/vps-provision.sh` را گسترش بده تا **PostgreSQL 18** را روی خود VPS نصب کند
      (نسخه فعلی Neon هم ۱۸.۴ است؛ نسخه پایین‌تر باعث مشکل در restore می‌شود)
- [ ] مهاجرت داده از Neon به VPS:
      `pg_dump` از Neon → `psql` روی VPS → مقایسه تعداد ردیف هر جدول قبل و بعد
- [ ] `DATABASE_URL` را در `.env.production` به دیتابیس محلی تغییر بده
      (`postgresql://gament:...@127.0.0.1:5432/gament`)
- [ ] **کپی بکاپ به مقصد دوم** — اسکریپت `gament-backup` فعلاً فقط روی خود VPS ذخیره
      می‌کند که در برابر از دست رفتن کل سرور بی‌فایده است
- [ ] Neon را **خالی نگه دار** به‌عنوان مسیر برگشت اضطراری؛ حذفش نکن
- [ ] بعد از مهاجرت، سرعت را اندازه بگیر و با عدد فعلی مقایسه کن
      (الان از سندباکس تا Neon حدود ۵۱۵ms طول می‌کشد)

⚠️ **قبل از مهاجرت حتماً یک بکاپ کامل از Neon بگیر و جایی امن نگه دار.**
